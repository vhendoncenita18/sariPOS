# Supabase email OTP as a post-password fallback

## Finding

Supabase supports the UI sequence “email + password, then choose TOTP or email code,” but its built-in email OTP is a **passwordless sign-in method**, not a native email MFA factor. Supabase documents MFA factors as TOTP and phone; it does not provide a built-in email factor challenge that upgrades the existing password session to AAL2. Email OTP sessions are AAL1. ([MFA overview](https://supabase.com/docs/guides/auth/auth-mfa), [AAL lookup](https://supabase.com/docs/reference/javascript/auth-mfa-getauthenticatorassurancelevel))

The relevant APIs are:

- First factor: `signInWithPassword({ email, password })`.
- TOTP path: `mfa.listFactors()` then `mfa.challenge({ factorId })` and `mfa.verify({ factorId, challengeId, code })`; successful factor verification promotes the session to AAL2. ([TOTP guide](https://supabase.com/docs/guides/auth/auth-mfa/totp), [MFA overview](https://supabase.com/docs/guides/auth/auth-mfa))
- Email-code path: `signInWithOtp({ email })`, with the email template containing `{{ .Token }}`, then `verifyOtp({ email, token, type: 'email' })`. Supabase documents this as logging in the user from an OTP. The result is conventional sign-in/AAL1, not an MFA upgrade. ([signInWithOtp](https://supabase.com/docs/reference/javascript/auth-signinwithotp), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp), [email templates](https://supabase.com/docs/guides/auth/auth-email-templates))

## Security and session consequences

Presenting the email-code choice only after a successful password check is possible as application UI sequencing. However, `signInWithOtp` + `verifyOtp` is independently a passwordless login path; the API does not document a binding to a prior `signInWithPassword` attempt. Therefore it must not be treated as proof that the same session completed two factors. On verification, Supabase returns a login session. In a shared `@supabase/ssr` client/cookie store this becomes the session used by the app; treat it as a new AAL1 login and verify the resulting JWT claims server-side. This session-replacement conclusion follows from the API being a login method and SSR storing the active session in cookies; Supabase docs do not explicitly describe this exact password-then-email sequence. ([verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp), [SSR package choice](https://supabase.com/docs/guides/auth/choosing-a-server-package), [SSR client setup](https://supabase.com/docs/guides/auth/server-side/creating-a-client))

Supabase also has `auth.reauthenticate()`, which sends a reauthentication nonce to an already signed-in user's email or phone. Docs describe it for sensitive operations such as secure password changes, not as an MFA login challenge or an AAL2 upgrade. ([reauthenticate API](https://supabase.com/docs/reference/javascript/auth-reauthenticate), [password auth guide](https://supabase.com/docs/guides/auth/passwords))

If the product accepts either TOTP AAL2 or email OTP AAL1 for access, encode that policy explicitly: routes may accept the normal authenticated AAL1 session, with TOTP raising assurance for the TOTP path. Do not label the email path “MFA” or claim it provides AAL2. Verify signed claims on the server (`getClaims()`/`getUser()`), and preserve `@supabase/ssr` cookie updates through the Next.js proxy/middleware response. Do not trust a client-selected method, a submitted user ID, or `getSession()` alone for authorization. ([AAL enforcement guidance](https://supabase.com/docs/guides/auth/auth-mfa), [SSR client setup](https://supabase.com/docs/guides/auth/server-side/creating-a-client))

## Email code delivery, resend, expiry, replay

- Use `{{ .Token }}` in the appropriate email template to send a numeric OTP. The template and project provider configuration must be set up; production email delivery should use custom SMTP. ([email templates](https://supabase.com/docs/guides/auth/auth-email-templates), [password-based auth](https://supabase.com/docs/guides/auth/passwords))
- For passwordless sign-in, request another code with `signInWithOtp` again. The documented `auth.resend()` endpoint is for signup confirmation, email change, SMS OTP, or phone change; it does not list generic passwordless sign-in email OTP as a resend type. ([signInWithOtp](https://supabase.com/docs/reference/javascript/auth-signinwithotp), [resend](https://supabase.com/docs/reference/javascript/auth-resend))
- OTP expiry is configurable under Authentication → Sign In / Providers → Email OTP expiration. Supabase recommends a reasonable short expiry; the production checklist suggests 3600 seconds or less, and the default email OTP expiry is documented as 24 hours in the JS reference overview. Set an explicitly shorter value suitable for a sign-in code. ([passwordless email guide](https://supabase.com/docs/guides/auth/auth-email-passwordless), [production checklist](https://supabase.com/docs/guides/deployment/going-into-prod), [JS auth reference](https://supabase.com/docs/reference/javascript/auth))
- Treat codes as one-use: invalid, expired, or already-used OTPs fail verification. ([OTP troubleshooting](https://supabase.com/docs/guides/troubleshooting/otp-verification-failures-token-has-expired-or-otp_expired-errors-5ee4d0))
- Current general Auth rate-limit docs list 2 emails/hour with built-in email delivery; `/auth/v1/otp` defaults to a 60-second per-user send interval; sign-in/OTP requests default to 30 per 5 minutes per IP; verify requests default to 30 per 5 minutes per IP. Custom SMTP can change email-send limits. A separate production checklist reports different OTP quotas, so use the project's live Authentication → Rate Limits settings as authoritative. Surface throttling errors and disable resend during the cooldown. ([Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits), [production checklist](https://supabase.com/docs/guides/deployment/going-into-prod))

## Next.js `@supabase/ssr` implications

Create a request-scoped server client for Server Actions. Auth calls that establish or replace a session must be allowed to persist refreshed/session cookies to the response; ensure proxy/middleware propagates the cookie mutations. Authenticate with verified claims or `getUser()` in trusted server code, and enforce the selected AAL policy there and in RLS where relevant. Avoid caching authenticated responses. ([SSR guide](https://supabase.com/docs/guides/auth/server-side), [client creation](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [advanced SSR guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide))

## Recommendation for the selected product policy

The selected policy “TOTP or email code; protected routes accept either” is implementable, but it means an email OTP login is an AAL1 alternative path, not MFA fallback. If requiring email + password before the email code is a security requirement, native passwordless OTP alone does not enforce that binding; a separate server-enforced transaction/challenge design is needed. Otherwise, describe it as “password sign-in, or email-code sign-in,” and reserve “MFA” for the TOTP route.
